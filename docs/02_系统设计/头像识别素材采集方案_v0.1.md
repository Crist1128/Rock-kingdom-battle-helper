# 头像识别素材采集方案 v0.1

> 本文专门记录“如何收集更多头像识别素材，让当前敌方头像识别更准确”的方案。  
> 当前目标不是重构识别架构，而是先把训练/评估/纠错素材积累起来，支撑后续优化模板匹配、定位和置信度判断。

---

## 1. 背景与问题

当前头像识别能力已经有初版：

- 可以上传战斗准备页截图；
- 后端会定位右侧敌方 6 个头像槽位；
- 使用本地头像模板做匹配；
- 前端展示 Top N 候选，用户逐槽确认。

但当前识别效果还不够好，主要原因不是业务流程问题，而是**可用于校准的真实素材太少**：

1. 图鉴头像和战斗准备页里的敌方头像存在差异：
   - 敌方头像朝向可能镜像；
   - 缩放、裁剪边界、圆形/黑底遮罩不同；
   - 游戏 UI 会压缩、抗锯齿、加阴影或混入背景。
2. 部分精灵颜色、轮廓非常接近，单靠图鉴模板容易混淆。
3. 截图来源会影响识别：
   - 分辨率不同；
   - Windows 缩放比例不同；
   - 窗口模式/全屏模式不同；
   - 游戏画质、亮度、录屏压缩不同。
4. 当前评估样本不足，难以判断改算法后是真提升还是只对某几张图过拟合。

因此后续应先做一轮**素材采集与标注体系**，把真实截图、头像裁片、标准答案和失败案例沉淀下来。

---

## 2. 采集目标

### 2.1 短期目标

先建立一个小而可靠的评估集：

- 20-50 张真实战斗准备页截图；
- 每张截图标注敌方 6 个槽位的正确精灵名称；
- 覆盖常见分辨率和窗口大小；
- 保留识别失败或低置信度案例；
- 每次优化识别算法后都能跑同一批样本评估 Top1 / Top3 命中率。

### 2.2 中期目标

建立可持续扩展的素材库：

- 收集更多真实敌方头像裁片；
- 为容易混淆的精灵建立“人工确认模板”；
- 按精灵编号、名称、来源截图、槽位记录元信息；
- 支持自动生成评估报告；
- 支持把用户确认结果反哺为后续模板或评估样本。

### 2.3 长期目标

如果模板匹配达到瓶颈，再考虑：

- 训练轻量头像分类模型；
- 使用特征向量检索；
- 引入更多游戏内 UI 识别，例如血条、名字、属性图标等。

但在评估集足够稳定之前，不建议直接上深度学习训练。

## 3. 需要收集哪些素材

### 3.1 完整战斗准备页截图

这是最重要的原始素材。

要求：

- 尽量保留原始截图，不要二次压缩；
- 优先使用 PNG；
- 不要裁掉右侧敌方阵容区域；
- 截图中敌方 6 个头像应完整可见；
- 文件名中尽量包含 6 个标准答案，方便初期快速解析。

推荐文件名：

```text
战斗准备_雪影娃娃1_寂灭骨龙2_尖嘴狐仙3_月牙雪熊4_龙息帕尔5_翠顶夫人6.png
```

含义：

- `雪影娃娃1` 表示第 1 槽是雪影娃娃；
- `寂灭骨龙2` 表示第 2 槽是寂灭骨龙；
- 依此类推到第 6 槽。

当前已有评估脚本可从类似文件名解析答案，因此早期可以先沿用这种命名方式。

### 3.2 每槽头像裁片

完整截图用于测试定位和整体识别，头像裁片用于分析单槽匹配问题。

建议保留两类裁片：

1. 自动裁剪结果：
   - 用当前算法从完整截图中裁出来；
   - 用于检查定位是否偏移。
2. 人工修正裁片：
   - 人工确认头像边界后裁出；
   - 可作为更干净的敌方实战模板。

推荐命名：

```text
001_雪影娃娃_slot1_from_20260704_001.png
002_寂灭骨龙_slot2_from_20260704_001.png
```

建议包含：

- 图鉴编号；
- 精灵名称；
- 槽位；
- 来源截图编号。

### 3.3 失败案例

失败案例比成功案例更有价值。

每次识别明显错误时，应保留：

- 原始截图；
- 当前算法裁出的 6 个头像裁片；
- 当前 Top N 候选结果；
- 正确答案；
- 错误类型。

错误类型建议：

| 类型 | 说明 |
|---|---|
| `slot_location_error` | 槽位定位偏了，裁到了背景或半个头像 |
| `similar_color_error` | 颜色相近导致误判 |
| `similar_shape_error` | 轮廓相近导致误判 |
| `mirror_error` | 朝向/镜像处理不对 |
| `scale_error` | 缩放差异导致匹配失败 |
| `template_missing` | 模板库里没有该精灵 |
| `db_mapping_missing` | 识别到模板但无法映射到数据库精灵 |
| `low_quality_screenshot` | 截图压缩或模糊严重 |

### 3.4 相似精灵对照素材

某些精灵容易互相误判，应主动收集对照组。

对照组示例：

- 同进化链；
- 同色系；
- 同体型轮廓；
- 多形态同编号；
- 图鉴头像和敌方头像差异明显的精灵。

对照组素材可以放在单独目录，方便后续针对性调权。

## 4. 推荐目录结构

建议后续素材不要散落在仓库根目录，而是集中到：

```text
data/rocom/recognition/
  elf_icons_128/
    # 图鉴头像模板，当前识别基础模板

  eval/
    screenshots/
      # 完整战斗准备页截图

    answers.json
      # 标准答案，可由文件名初步生成，再人工校正

    reports/
      # 每次算法评估输出

    debug_crops/
      # 自动裁剪结果，按评估批次保存

  confirmed_enemy_templates/
    # 人工确认过的敌方实战头像模板

  hard_cases/
    # 失败案例、混淆案例、低置信度案例

  similar_groups/
    # 相似精灵对照组
```

如果素材需要提交到仓库，应注意体积；如果素材过大，后续可以只提交少量标准评估集，其余保留在本地或单独压缩归档。

## 5. 标准答案格式

早期可以继续从文件名解析答案；中期建议增加结构化 `answers.json`。

示例：

```json
[
  {
    "image_id": "prep_20260704_001",
    "image_path": "screenshots/战斗准备_雪影娃娃1_寂灭骨龙2_尖嘴狐仙3_月牙雪熊4_龙息帕尔5_翠顶夫人6.png",
    "source": "manual_screenshot",
    "resolution": [1150, 643],
    "windows_scale": "100%",
    "game_mode": "windowed",
    "slots": [
      {"slot_index": 1, "elf_name": "雪影娃娃", "elf_id": null, "dex_no": null},
      {"slot_index": 2, "elf_name": "寂灭骨龙", "elf_id": null, "dex_no": null},
      {"slot_index": 3, "elf_name": "尖嘴狐仙", "elf_id": null, "dex_no": null},
      {"slot_index": 4, "elf_name": "月牙雪熊", "elf_id": null, "dex_no": null},
      {"slot_index": 5, "elf_name": "龙息帕尔", "elf_id": null, "dex_no": null},
      {"slot_index": 6, "elf_name": "翠顶夫人", "elf_id": null, "dex_no": null}
    ],
    "notes": "原始截图，未压缩"
  }
]
```

说明：

- `elf_name` 是人工确认的最低要求；
- `elf_id` 和 `dex_no` 可以后续用数据库自动补齐；
- `resolution`、`windows_scale`、`game_mode` 用于分析不同截图环境的影响；
- `notes` 用来记录特殊情况，例如截图模糊、遮挡、UI 缩放异常。

## 6. 采集流程建议

### 6.1 每次手动采集

1. 进入战斗准备页。
2. 截取完整游戏窗口，保存 PNG。
3. 按槽位顺序确认敌方 6 个精灵名称。
4. 使用推荐命名方式保存截图。
5. 跑当前识别命令生成结果和调试图。
6. 如果识别错误，把截图复制到 `hard_cases/` 并记录错误类型。

### 6.2 每次识别优化后

1. 对固定评估集跑批量识别。
2. 输出报告：
   - 总截图数；
   - 总槽位数；
   - Top1 命中率；
   - Top3 命中率；
   - 定位失败数；
   - 未映射模板数；
   - 平均耗时。
3. 对比上一次报告，确认是否真实提升。
4. 如果某些旧样本变差，不要只看总体提升，应记录回归风险。

### 6.3 用户确认结果反哺

后续可以在前端增加“保存为识别样本”的按钮，但必须满足：

- 用户已经确认 6 个槽位；
- 保存的是截图和确认结果，不直接改模板；
- 可选择是否保存调试裁片；
- 保存动作应明确提示本地路径；
- 不自动上传，不包含账号、Cookie 等敏感信息。

## 7. 识别优化优先级

有了素材后，建议按以下优先级优化。

### 7.1 先优化定位

如果头像框裁偏了，后面的模板匹配再强也会错。

重点检查：

- 右侧槽位整体偏移；
- 截图分辨率变化；
- 头像右边界被亮色区域截断；
- 黑色槽位检测误把头像暗部当槽位；
- 绿色血条检测是否稳定。

评估指标：

- 6 个槽位是否都定位出来；
- 裁片是否包含完整头像主体；
- 裁片是否混入太多血条、文字或背景。

### 7.2 再优化模板匹配

定位稳定后，再优化候选排序。

可尝试：

- 对人工确认敌方裁片建立模板；
- 对图鉴模板和实战模板分别打分；
- 给边缘轮廓、局部颜色、主体 mask 分别记录分数；
- 对同色系混淆样本降低颜色权重；
- 对轮廓差异明显样本提高边缘权重。

### 7.3 最后优化置信度

置信度不等于分数本身，应结合：

- Top1 与 Top2 分数差距；
- 定位可信度；
- 是否命中人工确认模板；
- 是否属于常见混淆组；
- 多帧或多裁剪变体是否稳定。

前端提示建议：

- `high`：可预选，但仍需用户确认；
- `medium`：展示 Top3，提醒检查；
- `low`：不建议自动预填，要求手动确认。

## 8. 素材数量建议

### 最小起步集

- 20 张完整截图；
- 120 个头像槽位；
- 覆盖 50 个以上不同精灵；
- 至少 5 张失败或低置信度截图。

### 可用评估集

- 50-100 张完整截图；
- 300-600 个头像槽位；
- 覆盖 150 个以上不同精灵；
- 每类常见错误至少 5 个案例。

### 较稳定评估集

- 200 张以上完整截图；
- 1200 个以上头像槽位；
- 覆盖主要热门 PVP 精灵；
- 常见分辨率和窗口模式都有样本；
- 有明确的版本化评估报告。

---

## 9. 不建议现在做的事情

在素材不足前，不建议优先做：

- 直接训练深度学习模型；
- 自动把识别结果写入敌方阵容；
- 用识别结果触发候选硬排除；
- 为了单张截图调死参数；
- 把失败样本直接覆盖进正式模板库而不记录来源；
- 大量提交未压缩、未筛选的截图素材到仓库。

当前更重要的是：

1. 收集真实截图；
2. 记录标准答案；
3. 保存失败案例；
4. 用固定评估集衡量每次优化是否有效。

---

## 10. 后续最小任务清单

如果后面继续做头像识别专项，建议先做这些小任务：

1. 建立 `data/rocom/recognition/eval/screenshots/` 和 `answers.json`。
2. 把当前已有测试截图整理进去。
3. 写一个小脚本，把文件名中的 `精灵名1...精灵名6` 初步转成 `answers.json`。
4. 扩展现有 `avatar_recognition_eval.py`，支持读取 `answers.json` 批量评估。
5. 每次识别输出：
   - Top1 命中率；
   - Top3 命中率；
   - 低置信度数量；
   - 定位方法统计；
   - 平均耗时。
6. 把最常错的 10-20 个槽位整理为 `hard_cases`，优先针对这些问题优化。

## 11. 与当前战斗系统的边界

头像识别素材采集只服务于提高“准备页敌方阵容候选推荐”的准确率。

它不改变以下原则：

- 事件流稳定优先；
- 状态快照可追溯；
- 候选推算不因识别结果直接硬排除；
- 识别结果必须经过用户确认；
- 批量导入或素材同步必须可 dry-run、可解释、可回滚。
