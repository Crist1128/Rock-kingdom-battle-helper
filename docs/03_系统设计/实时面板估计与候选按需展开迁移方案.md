# 实时面板估计与默认配置校验落地方案

> 更新时间：2026-06-08
> 状态：主流程已切换。`build_candidate` 不再由业务主流程生成、读取或更新；Observation、伤害事件和自动结算伤害默认只写实时估计 evidence。按需配置展开子方案已撤销；默认配置由玩家选择并由后端按实时约束校验。复杂公式、天气/状态反推、速度概率和事件重放仍待实现。
> 目标：敌方配置推算彻底改为“实时面板估计 + 约束推导 + 默认配置校验”。

## 1. 背景

当前候选推算流程会在准备阶段为敌方精灵生成候选配置，并在战斗中根据 Observation 更新候选 `match_score`、`confidence` 和 evidence。这个方案直观、容易解释，但在候选空间扩大时会带来两个明显问题：

1. 准备阶段需要生成和落库大量候选，占用时间和空间。
2. 每次观测可能读取并更新大量候选，SQLite 写入压力随候选数量线性增长。

为了避免因为缩小候选空间造成漏判，同时降低数据库读写压力，当前主流程已经转向实时估计：默认不预生成全量候选，而是保存玩家选择的默认配置和当前推导出的属性约束；保存默认配置时按实时约束校验完整面板。

## 2. 总体思路

新的主流程：

```text
录入敌方精灵
  -> 玩家选择默认配置方案
  -> 系统按默认配置计算一个临时展示面板
  -> 战斗观测进入实时推导
  -> 更新 HP/物防/魔防/物攻/魔攻/速度等属性范围
  -> 前端用“默认面板 + 推导范围 + 置信状态”展示
  -> 用户需要时再按需临时展开可能性格/资质组合
  -> 展开过程只在内存中运行，不写 build_candidate
```

核心变化：

| 旧候选主流程 | 新实时估计主流程 |
| --- | --- |
| 准备阶段生成候选并落库 | 准备阶段只保存默认配置和估计档案 |
| 每次观测更新很多候选行 | 每次观测更新少量约束摘要 |
| 候选 `confidence` 作为主展示 | 属性范围和推导证据作为主展示 |
| Top 候选随时从库里查 | Top/可能配置按需临时展开 |
| 候选表是核心状态 | 估计档案是核心状态，候选表标记为待删除遗留结构 |

## 3. 设计目标

1. 降低准备阶段成本：不再默认生成几百到几万候选。
2. 降低战斗中写入成本：Observation 默认只更新估计档案，不逐候选写分数。
3. 保留解释能力：每次推导仍要记录观测来源、公式上下文、unknown factors 和置信状态。
4. 保留查看可能配置能力：按需在内存中展开，不再把候选空间作为业务状态。
5. 避免漏判：默认配置只用于展示初始面板，不能作为排除其它配置的依据。
6. 继续坚持 unknown 优先：公式、状态、应对、减伤、速度因素不完整时，只扩大不确定范围，不硬覆盖真实估计。

## 4. 非目标

第一阶段不做：

- 本阶段不立刻删除现有 `build_candidate` 表，但已标记为后续迁移删除。
- 旧 `/candidates/*` 接口不再挂载。
- 不把实时估计结果宣称为已确认真实配置。
- 不完整反推出唯一配置；当前只在普通攻击最小公式上下文完整时写入低置信属性范围。
- 不在未知因素存在时强行收窄范围。
- 不一次性重写所有 Observation matcher。

## 5. 核心概念

### 5.1 敌方面板估计档案

建议新增概念：`EnemyPanelEstimate` 或 `EnemyEstimateProfile`。

它不是候选列表，而是“当前我们对敌方面板的认知状态”。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `estimate_id` | 估计档案 ID。 |
| `battle_id` | 所属战斗。 |
| `battle_elf_state_id` | 对应敌方战斗精灵状态。 |
| `elf_id` | 敌方精灵 ID。 |
| `default_config_json` | 玩家选择的默认配置方案。 |
| `default_panel_json` | 按默认配置计算出的临时展示面板。 |
| `estimated_panel_json` | 当前用于展示的估计面板，可包含具体值或范围。 |
| `stat_constraints_json` | 六维属性约束范围。 |
| `confidence_json` | 各属性置信状态。 |
| `unknown_factors_json` | 当前仍影响判断的不确定因素。 |
| `evidence_summary_json` | 最近推导摘要。 |
| `updated_by_event_id` | 最近一次更新估计的事件 ID。 |

### 5.2 默认配置

默认配置由玩家选择，主要解决“对面真实面板未知时仍要有一个可看的面板”的问题。

示例预设：

- 极速默认：正速度、速度资质 10，另外两个主流维度 9/10。
- 满攻默认：正物攻或正魔攻，攻击资质 10。
- 均衡默认：常见主流三维投入。
- 自定义默认：玩家手动选择性格和资质。

默认配置只影响初始展示，不参与硬排除。

### 5.3 属性约束

实时推导的核心不是候选分数，而是属性范围：

```json
{
  "hp": {"min": 450, "max": 488, "source": "hp_percent_delta"},
  "physical_defense": {"min": 260, "max": 292, "source": "damage_value"},
  "magic_defense": {"min": null, "max": null, "source": "unknown"},
  "physical_attack": {"min": null, "max": null, "source": "unknown"},
  "magic_attack": {"min": 315, "max": 340, "source": "damage_value"},
  "speed": {"min": 313, "max": null, "source": "speed_order"}
}
```

约束可以是：

- 区间：`min/max`。
- 不等式：速度大于或小于某值。
- 集合：可选面板值集合。
- unknown：当前信息不足。

## 6. 推导规则

### 6.1 敌方受到攻击

敌方作为防御方时，用我方攻击观测反推敌方防御侧属性。

物理技能：

```text
观测伤害 + 我方攻击面板 + 技能上下文
  -> 推导敌方物防范围
  -> 如果有扣血百分比，同时推导敌方 HP 范围
```

魔法技能：

```text
观测伤害 + 我方攻击面板 + 技能上下文
  -> 推导敌方魔防范围
  -> 如果有扣血百分比，同时推导敌方 HP 范围
```

注意：

- 只有整数伤害时，HP 通常无法稳定反推。
- 只有扣血百分比时，防御也无法稳定反推。
- 同时有整数伤害和掉血百分比时，HP 与防御约束会明显更有价值。
- 如果存在减伤、防御技能、应对成功、状态修正、天气修正未知，必须保留 unknown，不硬收窄。

### 6.2 敌方攻击我方

敌方作为攻击方时，用我方受击观测反推敌方攻击侧属性。

物理技能：

```text
观测伤害 + 我方防御面板 + 技能上下文
  -> 推导敌方物攻范围
```

魔法技能：

```text
观测伤害 + 我方防御面板 + 技能上下文
  -> 推导敌方魔攻范围
```

注意：

- 技能分类未知时，不推导物攻/魔攻，只记录 unknown。
- 技能威力、属性克制、本系、应对、减伤、天气、状态修正缺失时，只记录低置信范围或 unknown。
- 连击优先使用单段伤害推导攻击属性，总伤害只用于 HP 变化和击杀判断。

### 6.3 速度推导

速度单独作为不等式约束处理。

```text
我方先手 -> 敌方速度 <= 我方有效速度
敌方先手 -> 敌方速度 >= 我方有效速度
同速表现 -> 速度接近或存在同速随机
```

如果存在以下因素，速度推导降级为 unknown：

- 技能优先级不同。
- 先制或后手效果。
- 速度状态修正。
- 天气或场地速度修正。
- 同速随机无法确认。

### 6.4 技能出现

技能出现不再默认更新每个候选，而是更新估计档案中的技能事实：

```json
{
  "confirmed_skill_ids": ["skill_x"],
  "skill_pool_status": "seen",
  "evidence_event_ids": ["event_1"]
}
```

技能事实可用于后续伤害上下文解析，也可在按需展开候选时过滤不可能技能池，但第一阶段不作为硬排除主流程。

## 7. 约束合并策略

每次 Observation 产生一个局部约束，系统需要合并到当前估计档案。

建议规则：

| 新结果 | 合并方式 |
| --- | --- |
| 明确区间 | 与旧区间取交集。 |
| 明确下界/上界 | 更新对应边界。 |
| 与旧约束冲突 | 不直接覆盖，记录 conflict evidence。 |
| 存在 unknown | 不收窄或只生成低置信宽范围。 |
| 观测被作废 | 后续事件重放时从历史事件重新生成估计档案。 |

冲突处理必须保守。比如新推导区间与旧区间没有交集时，不应直接清空估计，而应记录：

```text
constraint_conflict:
  old: hp 450-488
  new: hp 510-530
  possible_reason: damage_reduction_unknown / wrong_observation / formula_gap
```

## 8. 默认配置校验

新方案不是落库候选空间，也不再临时展开可能配置。玩家选择默认展示配置时，由后端即时计算面板并按当前约束校验。

默认配置保存流程：

```text
玩家选择性格和资质
  -> 前端按明确推导出的主属性做轻量禁用
  -> 后端计算完整六维面板
  -> 后端按 stat_constraints_json 校验 integer_min / integer_max
  -> 合法则保存 default_config_json / default_panel_json / estimated_panel_json
```

规则：

- HP/双防约束只用于校验完整面板，不用于枚举候选空间。
- 已明确推导出物攻、魔攻或速度时，前端可收紧为对应正修性格并要求对应资质投入。
- 保存失败时返回冲突属性，由前端展示给玩家调整。
- 不在准备阶段或战斗中展开候选配置。

## 8.5 天气/状态反推规划

天气、异常、印记、场地和技能槽效果不应回到旧候选空间方案，而应作为实时估计的公式上下文来源：

```text
BattleEffectSnapshot.full_snapshot_json
  -> ModifierResolver / ResponseResolver / 后续 WeatherResolver
  -> 生成结构化 modifier_context
  -> EstimateService 根据 modifier_context 推导属性范围或记录 unknown
```

规划原则：

- 历史事件必须读取事件发生时的 `BattleEffectSnapshot`，不能读取当前状态冒充历史状态。
- 天气/状态 modifier 已解析时，写入 `formula_context_json` 和 `inferred_stats_json`。
- 天气/状态 modifier 未解析时，只写 `unknown_factors_json`，不收窄属性约束。
- 状态伤害、星陨、寄生、灼烧等非普通攻击伤害先按来源类型拆分反推规则，不能强行套普通攻击公式。
- 速度相关天气/状态先生成不等式约束或 unknown，不通过候选速度桶计算概率。

## 9. 数据库设计建议

第一阶段建议新增两张表，或者先用一张表内 JSON 承载，后续再拆。

### 9.1 `enemy_panel_estimate`

用途：保存每只敌方精灵当前估计档案。

建议字段：

```sql
CREATE TABLE enemy_panel_estimate (
  estimate_id TEXT PRIMARY KEY,
  battle_id TEXT NOT NULL,
  battle_elf_state_id TEXT NOT NULL,
  elf_id TEXT NOT NULL,
  default_config_json TEXT,
  default_panel_json TEXT,
  estimated_panel_json TEXT,
  stat_constraints_json TEXT,
  confidence_json TEXT,
  unknown_factors_json TEXT,
  confirmed_skill_ids_json TEXT,
  evidence_summary_json TEXT,
  updated_by_event_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

建议索引：

```sql
CREATE INDEX idx_enemy_panel_estimate_battle_elf
ON enemy_panel_estimate(battle_id, elf_id);

CREATE INDEX idx_enemy_panel_estimate_state
ON enemy_panel_estimate(battle_elf_state_id);
```

### 9.2 `enemy_panel_estimate_evidence`

用途：保存每次估计变化的解释链，避免把长 evidence 全部塞进估计档案 JSON。

建议字段：

```sql
CREATE TABLE enemy_panel_estimate_evidence (
  evidence_id TEXT PRIMARY KEY,
  estimate_id TEXT NOT NULL,
  battle_id TEXT NOT NULL,
  source_event_id TEXT NOT NULL,
  observation_type TEXT NOT NULL,
  inferred_stats_json TEXT,
  constraint_delta_json TEXT,
  formula_context_json TEXT,
  unknown_factors_json TEXT,
  conflict_json TEXT,
  confidence TEXT,
  created_at TEXT NOT NULL
);
```

`source_event_id` 只作为来源引用，不强制外键到 `battle_event`。Observation API 可能写入 `observation_<uuid>` 这类轻量观测 ID，未必对应一条通用战斗事件。

第一阶段如果想少建表，也可以先把最近 evidence 摘要放在 `enemy_panel_estimate.evidence_summary_json`，但长期建议拆表。

## 10. 接口设计建议

旧候选接口已下线，保留估计接口。

建议新增：

| 接口 | 说明 |
| --- | --- |
| `GET /api/v1/estimates/{battle_id}/{elf_id}` | 查询敌方面板估计档案。 |
| `PUT /api/v1/estimates/{battle_id}/{elf_id}/default-config` | 设置玩家默认配置方案。 |
| `GET /api/v1/estimates/{battle_id}/{elf_id}/evidence` | 查询估计 evidence。 |
| `POST /api/v1/estimates/{battle_id}/{elf_id}/recompute` | 从事件重放重算估计档案。 |

现有 Observation API 已固定写入实时估计；`allow_hard_exclude` 仅作为废弃兼容字段存在。

## 11. 前端设计建议

候选面板应逐步改成“敌方面板估计”视图。

建议展示结构：

1. 顶部显示敌方精灵和当前估计状态。
2. 默认配置选择器：极速、满攻、均衡、自定义。
3. 六维面板展示：
   - 默认值；
   - 推导范围；
   - 当前展示值；
   - 置信状态。
4. 观测证据列表：
   - 伤害事件；
   - 推导出的属性；
   - unknown factors；
   - 冲突说明。
5. 可选按钮：
   - 查看可能配置；
   - 重新计算估计；
   - 采用某个展开配置作为展示面板。

旧候选 Top5 不再是主视图；当前主视图是实时估计、约束范围、unknown factors 和按需展开结果。

## 12. 迁移路线

当前迁移状态：

### 阶段 1：新增估计档案

- 新增估计档案表和 schema。

- 前端可手动设置默认配置。
- 已完成。

### 阶段 2：Observation 写实时估计

- 伤害和速度观测进入实时估计 evidence。
- 不再写旧候选软评分。
- 已完成。

### 阶段 3：估计档案成为默认展示

- 战斗工作台默认展示实时估计面板。
- 可能配置通过内存展开展示。
- 已完成。

### 阶段 4：准备阶段不再自动生成候选

- 新战斗默认只创建估计档案。
- 已完成。

### 阶段 5：旧候选遗留清理

- `build_candidate` 不再是主推算状态。
- `/candidates/*` 已不再挂载。
- 下一步确认存量兼容后删除旧表、旧 service/schema/tests。

## 13. 性能预期

新方案的数据库写入量主要随“事件数量”增长，而不是随“候选数量”增长。

| 操作 | 旧方案成本 | 新方案成本 |
| --- | --- | --- |
| 准备阶段 | 生成并写入候选 | 创建估计档案 |
| 单次伤害观测 | 读写大量候选 | 写少量约束和 evidence |
| 展示当前面板 | 查 Top 候选 | 读估计档案 |
| 查看可能配置 | 直接查候选表 | 临时枚举并过滤 |
| 事件重放 | 需要重放候选分数 | 从事件重建估计约束 |

新方案把压力从 SQLite 写入转移到按需 CPU 计算。由于按需展开不是每次事件都触发，整体更适合本地 SQLite MVP。

## 14. 风险与边界

1. 实时推导依赖公式完整度。公式缺失时只能给 unknown，不能假装收敛。
2. HP 与防御通常存在耦合，单次伤害不一定能唯一确定面板。
3. 玩家默认配置可能与真实配置差异很大，必须明确标注“默认展示”而不是“已确认”。
4. 冲突处理比候选扣分更复杂，需要完整 evidence。
5. 事件作废和重放会更重要，因为估计档案是由事件累计推导出来的。
6. 按需展开仍可能消耗 CPU，但不会造成持续数据库写入压力。

## 15. 测试建议

第一批测试应覆盖：

- 阵容录入后创建默认估计档案。
- 玩家设置默认配置后，默认面板正确刷新。
- 我方物理伤害推导敌方物防范围。
- 我方魔法伤害推导敌方魔防范围。
- 我方伤害 + 扣血百分比联合推导敌方 HP 范围。
- 敌方物理攻击推导敌方物攻范围。
- 敌方魔法攻击推导敌方魔攻范围。
- 速度先后手生成速度上下界。
- unknown factors 存在时不收窄或只生成低置信宽范围。
- 事件作废或重放后估计档案可重算。
- 按需展开候选不写入全量候选表。

## 16. 与旧候选方案的关系

旧候选空间方案已放弃作为业务方案。当前仅保留：

- `build_candidate` 表：待 Alembic 删除。
- `CandidateService` / `Candidate*` schema / candidates endpoint 文件：待代码清理。
- 旧候选测试：待重构或删除。

所有新功能必须基于 `EnemyPanelEstimate`、`EnemyPanelEstimateEvidence`、默认配置校验和事件流重算，不得重新引入候选空间落库筛选。
